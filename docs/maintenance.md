# 内容维护

## 给旧事件补一条证据

以 Kimi 的权重从预告变为可下载为例，这件事能回答旧档案留下的问题。“后来怎样了”可以沿原来的事件 ID 继续读。[三个观察日及字段对照](map-design.md#同一份-kimi-档案的三个观察日)

1. **先定补哪一条。** 在 [data/map.json](../data/map.json) 找到 `kimi-k31-pro-release`。核对原公告与后来可取得的权重文件，按[近期选材规则](../PROJECT_RULES.md#近期选材)给出补注理由，等用户确认采用。
2. **登记依据。** 查 `sources` 里是否已有该出处，有就复用 ID。新来源记下链接、发表日、查阅日和它能证明的范围。Kimi 的权重文件能证明文件已可取得，单凭它还无法评价部署效果。未核实的线索留在内部研究，需保留比较判断时用 `research/audits/`。
3. **把新判断接回原档案。** 保留事件 ID、首发日和 `then`。在 `later` 写明截至哪天可以作出什么判断，把依据列入 `later.source_ids`，也收进事件的 `source_ids`。若还有一则需要按另一日期单独阅读的报道，可参照本例 11 月 18 日的材料，保留它自己的出处和日期。同一事件在各入口共用这份记录。
4. **从读者入口验收。** 运行下列命令，打开离线网页，从「模型系列」点 Kimi。在 10 月 23 日能读到首发判断，11 月 18 日出现对手的同期评测，11 月 20 日才读到权重可取得的回看。再打开[系列文字版](../chronology/series/README.md#event-kimi-k31-pro-release)，对照两条回看的日期，并检查出处是否贴合正文。

## 校验与生成

```powershell
node scripts/check.mjs
node --test scripts/check.test.mjs
node scripts/build.mjs
```

[check.mjs](../scripts/check.mjs) 检查稳定 ID、日期、引用和关系等约定。[build.mjs](../scripts/build.mjs) 先调用同一校验，再读取 `web/` 下的 HTML、CSS 和 JavaScript，把界面与地图数据打包成 `dist/index.html`，并从同一数据生成 `chronology/` 的年表、系列和专题。内容问题回到 `data/map.json` 修改，呈现问题查 `web/` 或对应的文字版构建代码，再重新生成。

交互修改后检查年度选择、主次展开、详情、相关跳转、返回与窄屏。纯内容修改检查数据与对应页面，不机械写镜像实现的测试。

## 改动其他入口时查哪里

对象及用途见[内容数据](map-design.md#内容数据)。系列通过 `event_id` 引用共用事件，每项须说明关联理由并区分 key/supporting。条目按事件日期及 ID 排序，非末关键站必须有转场。系列 as_of 不得超出内容包日期，覆盖说明须明确截止和缺口。系列关键站与年度主线分别选取。

分支未指定展示父节点时，自动进入平级的月份同期组；不能恢复按关系数组首项或邻近日期挂接。修改推荐路线时同步检查转场、跨年下一站与退出路线；路线引用现有事件，不复制正文。系列交互另查跨年、补充节点关闭后焦点、系列外事件返回、刷新与历史。README 提供读者入口，内容范围可由地图数据和公开版本记录核对。

`updated_at` 是整包内容更新日；各年 `as_of` 保留该年的核验截止日。只补历史年份时，不把进行中年份的截止日一起改成今天。

系列入口可用 `series_timeline` 选取一段连续月份。每行对应一个模型家族，用已有事件 ID 与短标签标出确切日期，也可以选入尚无独立系列的家族。观察日决定可见节点和回看日期。试读节点沿用原档案的 `then` 与 `later`，分别写明当时可知的事实、后来模型自身的变化及对手带来的新选择。网页和系列目录文字版共用这份选材。

节点的 `kind` 取自 `series_timeline.legend.kinds`，按该日发生的主要变化标记。类型的底色、符号和名称都由这份图例给出。日期旁的“已有回看”标签随观察日出现。构建会把同款标签写入 `chronology/series/legend-*.svg`，供文字版和 README 离线显示。调整试读节点时，同步 README 的示例。

首页的 `recent_update` 保存本期选材截止、导语和事件 ID。换期时替换这组引用，最多选三件在首页直接展示，其余仍可展开。专题放在可选的 `topics` 中。首篇各用一项已有事件和该事件的一条出处解释交付物、人还要做什么、材料能证明什么，再给出一则有理由的延伸阅读。网页与年表由同一次构建生成。

需要按时间比较同一任务时，给专题案例加 `history`，写任务名、适用人群和几条有日期的早期材料。每步按所引原文的发表月展示，说明当时的交付物和人的工作。终点引用已有事件，事后核验写进该事件的 `later`，网页详情和专题文字版都能读到。

比较价格时写清比较对象、任务、计量单位和观察日期。比较赛况时交代规则与作品出处，社区投票、厂商演示和独立测试各按自身范围引用。有可对照的材料再组织专题。

当前任务与选材、年度关键词、事实更正的简短修订收据进入 本地维护记录。旧核验日期保留在内部来源档案；旧 CH/EX 等仅为历史标识，不代表仍有章节要写。

系列关键站必须提供事件 change，页面据此展示“为什么重要”；转场要接住前一站的具体问题，并在下一站正文中得到回应。每系列通常保留5—8个关键站，不将每次最新发布自动升级。阅读次序已由series表达，不再为相邻站机械复制context关系；事实联系、跨系列采用与值得展开的分支才进入relations。

系列outro总结阶段变化，exit只选一个有具体理由的非关键站出口，事件日期不晚于系列截止。supporting条目用return_to指定本系列关键站及衔接理由；不使用通用“继续下一次变化”代替解释。修改后检查末站、出口、补充分支返回和历史恢复。个人使用自述须写明型号、环境及可证明的范围；持续修订的评测不能冒充首版快照，后续材料不得混入首发成绩。

## 从本地试读到公开发布

本地试读通过后，在收到提交、推送与发布的授权时，先对照公开仓库当前版本，从本轮改动中选取公开数据、界面、构建脚本及配套文档。研究收据、作者素材和内部总账留在工作区。网页引用外部材料时默认用链接或必要短引，图片和音视频另核再发布权。

推送后核对公开分支的提交和对应的 Cloudflare 构建结果。最后从线上首页走一次受影响的阅读路径，看到预期的内容、日期和出处，再把公开提交和试读结果记入总账。日常选材由用户手动触发。
